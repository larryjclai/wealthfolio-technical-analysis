# 開發與發布指南

## 版本管理

從 1.0.0 起採用 [語意化版本（SemVer）](https://semver.org/lang/zh-TW/)，以 `主版號.次版號.修訂號` 表示：

| 變更 | 範例 | 本套件判斷方式 |
| --- | --- | --- |
| 修正錯誤、文案或相容的介面微調 | 1.0.0 → 1.0.1 | 不增加新能力，也不破壞既有用法 |
| 新增相容功能 | 1.0.1 → 1.1.0 | 增加新指標或提醒方式，原設定仍可正常使用 |
| 不相容變更 | 1.1.0 → 2.0.0 | 改變既有介面契約、計算定義或設定用法，造成相容性中斷 |

- `0.x.y` 表示尚未穩定的初期開發，不用來表示 1.0.0 之後的小修正。
- 每次修改不必立即升版。開發中先累積於 [CHANGELOG.md](../CHANGELOG.md) 的「尚未發行」，準備交付新版安裝包時再依整批變更升版。
- 已交付的版本之後若有內容變更，使用新版本，不覆蓋同版內容；測試版可用 `1.1.0-beta.1`。
- 每次發行同步 `package.json`、`package-lock.json` 與 `manifest.json`，重新封裝 `addon.zip`。Git commit 記錄日常修改，正式發行時可建立 `v1.0.1` 這類標籤，兩者不等於每次都要升主版號。
- 本次依使用者要求將先前的 2.x 編號一次性重定為 1.0.0；後續依上述規則遞增，不再反覆重設。此編號重定不能視為一般由小到大的自動更新，主程式安裝行為仍需以實際匯入檔案確認。

## GitHub Release 發布流程

- 每次 Release 都需提供版本更新說明，先將完整文案交由專案擁有者確認或修正，取得明確同意後才公開發布；commit、push 或交付安裝包不代表文案已獲核准。
- 核准前將文案保存在 `docs/release-版本號.md`，或建立 GitHub Draft Release；不自動公開。
- 發布時確認程式與安裝包版本一致、驗證通過，再提交並推送對應程式碼，建立指向該提交的 `v版本號` 標籤。
- GitHub Release 附上核准的更新說明與該版本的 `addon.zip`，完成後確認下載檔與版本正確。
- 尚未公開的草稿不算正式發行；不為沒有對應可驗證程式碼／安裝包的舊版補造 Release。

## 開發與驗證

```sh
npm install
npm run type-check
npm test
npm run bundle
```

`bundle` 會重新建置並產生全新封裝，避免舊檔案殘留。`dist/` 與 `manifest.json` 包含於封裝，不含預覽資料。

本機模擬資料預覽：執行 `npm run preview:fixtures`，開啟終端顯示的本機網址並加上 `/tests/preview.html`。這個頁面使用合成行情、假交易與記憶體儲存，不會連到真實帳戶，也不是正式安裝。

專案原有的 `lint` 指令尚未配置 ESLint；本次以包含測試檔的 TypeScript 檢查、Vitest 與建置驗證為準。
